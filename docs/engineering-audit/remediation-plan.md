# Halo 修复路线与验收依赖

审计日期：2026-10-13（Asia/Shanghai）。来源分支：`1.20.1-fabric`；审计文档分支：`review/2026-10-13`。

Halo 基线：`49b822c037606faaf0bb8ba2adba7b63ce0d62bb`；锁定 HaloCore：`a22160a842e15fffb1bc03b5b189183557f6d510`（2.5.0）。所有源码行号指向这两个提交，不指向后续修复版本。

本阶段只做审计，以下为后续建议，不代表已修改或修复。范围跨Halo与HaloCore时先在core提交和验证，再在Halo更新锁定gitlink；不要自动跟随core main。每个阶段都在明确分支处理，保留当前审计基线作对照。

## 前置契约

先确认佩戴definition ID的统一有效集、文件写失败时是否允许仅会话生效、JSON树/几何预算和错误资源发布策略。这些契约决定错误反馈、迁移与测试，不应在各command/codec/parser中分别实现互不相容的规则。保持现有wire字段、NBT list格式及api.v2方法描述符，除非另行制定迁移。

## 跨阶段验收

先为已确认问题加入能复现失败的行为测试，在修复前确认测试失败；测试必须调用真实生产parser/上传计划/存储入口，而不是复制相同公式。HALO-013应贯穿阶段1–10。

```sh
# core变更的基本门禁
./core/gradlew -p core build --console=plain
# Halo + 锁定core、wire/NBT、打包、旧API门禁
./gradlew build --console=plain
# 发布脚本变更时才运行此项
python3 -m unittest discover -s scripts/release -p 'test_*.py' -v
```

| 场景 | 修复后的行为验收重点 |
| --- | --- |
| 单人、专用服双客户端、LOCAL | 正常show/hide/重连；失败输入不影响其他玩家或旧状态 |
| 死亡/重生、跨维度、untrack/track | 暂时不可见不撤销所有权；非法旧记录有可恢复诊断 |
| resource/data reload | 坏资源隔离、预算拒绝、有效资源发布、旧资产回收 |
| compatibility/cached、world/GUI | 不重启动画/物理；quad确实使用缓存，fallback有明确原因 |
| Iris/EMF/YSM | 固定版本和ABI，资源重载/光影开关；记录外部包缺失的跳过 |
| 文件故障 | 旧文件仍可读、写入状态反馈准确、重启与会话值按契约一致 |
| 规模 | N/E操作数、heap/direct/GPU分配及长期历史cache，不把微基准等同TPS |

真实游戏测试应使用DEVELOPMENT.md的隔离runSmoke目录，不接触生产世界；指定第三方包时记录版本与哈希，不把授权不明的包加入仓库。发布验收报告分别列出通过、失败、跳过和未执行。

## 集成与发布顺序

1. 同步实现core契约和定向测试，core独立build/边界/fixture通过，记录新SHA。
2. Halo适配器基于该SHA联调，在同一功能分支更新gitlink；联合build、分发类检查、旧api.v2调用方通过。
3. 完成受影响的游戏/文件故障/资源规模验证；确认疑似风险是否升级、关闭或继续未知。
4. 只按维护需要移植其他平台分支，每个目标独立验证Mixin、网络和图形API；不自动批量更新所有core指针。
5. 另行执行发布任务时遵守core在前、Halo在后及Release正文定稿门禁。审计本身不授权修改外部系统，本次不触发tag/release/平台上传。

下一次复审应保留旧失败输入并记录新source SHA、core lock、测试统计及实际fallback/内存证据，而不是仅写“已优化”。
