# Halo 深入工程审计报告

审计日期：2026-10-13（Asia/Shanghai）。来源分支：`1.20.1-fabric`；审计文档分支：`review/2026-10-13`。

Halo 基线：`49b822c037606faaf0bb8ba2adba7b63ce0d62bb`；锁定 HaloCore：`a22160a842e15fffb1bc03b5b189183557f6d510`（2.5.0）。所有源码行号指向这两个提交，不指向后续修复版本。

## 结论

主线有清楚的core/平台边界、固定子模块来源、兼容调用方检查和较丰富的数学/行为测试，但输入预算、错误恢复与对象所有权仍有实质缺口。最先处理服务端C2S数量驱动分配，以及佩戴ID在持久化和来源API之间的契约冲突。

发现15项：12项已确认、2项疑似风险、1项改进建议；P1×2、P2×12、P3×1。**本次未确认P0**，这不代表完成了渗透测试或可以声明零漏洞。每项的文件/行号、条件、影响、置信度、建议、验证和工作量均列在[findings.md](findings.md)。

本次交付只包含审计文档，不修改Java/Python/Gradle/资源或core gitlink，不运行发布、不push远端。新分支从主线固定基线创建。

## 方法与证据等级

先读取AGENTS/开发指南，按锁定提交获取core；清点技术栈/资源/测试/CI；沿命令→存储→仲裁→网络→客户端→渲染以及资源→解析→CPU/GPU缓存逐层阅读。审查与编译均在独立克隆内进行，不使用生产世界、服务账号或真实凭据。

证据分为：实际生产core类的隔离行为复现；实际适配器存储类配轻量平台桩的复现；源码可直接证明的错误/缺口；仅能由具体游戏/GL/聊天场景确认的风险。后两类不会用“测试通过/可编译”冒充端到端验收。源行号固定到基线，后续修复应重新生成。

所有探针有界运行，巨大count的OOM只在64 MiB子进程中触发并捕获；百万ring仅确认解析和预算公式，没有申请超大几何。没有攻击在线服务。检查结果/探针代码在[verification-baseline.md](verification-baseline.md)可重放。

## 功能正确性与API契约

HALO-002是写入顺序和ID契约组合错误：相同 `halo:` 字符串被资源 Identifier 接受、被HaloSource拒绝，却已经写入world_data；恢复再触发同一异常。修复要覆盖新写入和已有NBT，而非只给指令做前端校验。

HALO-003的索引/顶点混淆让缓存quad必然触发数组越界。错误在工厂中被memoize并落到CPU fallback，所以绿色构建/正常画面都不能证明缓存路径正常；需要上传计数和工厂结果。它也影响发光billboard，因为缓存构造总会创建受光布局。

HALO-009的动画数组所有权缺口可由合法调用结果直接污染共享cache；边界返回和中间插值的所有权不同，尤其容易让调用方作出错误假设。当前内部renderer主动写这些数组的证据不足，风险主要集中在扩展/后续维护。

没有把专用服不分发调试config、客户端各自定义缺失、mesh透明度不是全局OIT、外部来源需重新提交等明确设计当成bug。

## 异常处理、边界与数据完整性

HALO-004直接复现单个null叶子导致后续有效本地记录没有加载，然后被下一次正常show覆盖丢失。HALO-005是local/config直接覆盖文件的故障恢复缺口；真实断电未测，但旧文件在写入开始即失去保护的写法已经确认。HALO-006补足另一种问题：优先级writer虽用原子移动，异常却被吞掉，命令仍称已保存。原子写和正确反馈是两个独立要求。

资源入口的错误隔离只处理普通异常。HALO-007以15 KiB深层合法JSON在较小线程栈下复现StackOverflowError，默认JVM栈下60 KiB/4000层也复现；HALO-008以小JSON触发可扩展到百MiB级的几何预算。二者都来自选中的资源包/数据包，而不是已经证明可被任意远端客户端送入的资源攻击。对JSON读取、树结构和几何分别设边界，不能用捕获OOM/StackOverflow代替预算。

## 并发、异步与资源释放

网络的业务状态变更使用server.execute/client.execute，server host验证owner线程；资源catalog以synchronized/volatile快照交接；PreviewSession与world physics隔离。这些现有措施降低了常见跨线程共享实例问题。

HALO-012为待确认的嵌套world捕获不对称：非living begin不push、end却pop；单值ThreadLocal也不能恢复上一层。coordinator状态机模拟支持该风险，但没有实际nested renderer证据。Mixin RETURN钩子不能覆盖所有异常退出，需结合具体宿主异常恢复策略验证。

GPU cache在代际或mesh变化时释放移除资源；native upload staging显式free并先摘除storage，已有防double-free处理。没有发现足以确认常态GPU/native泄漏的证据。HALO-011则是已复现的CPU资产历史引用保留：published资源已经空，loader仍持有40个模型。它只在同代际依赖轮换中增长，不是每帧重复加载，也不是无法释放的永久进程泄漏。

## 安全与敏感数据

HALO-001是最明确的服务端攻击面：无管理员门槛的C2S数量字段直接决定集合容量，并在网络线程解析期间触发OOM。确认了危险分配和可达路径；具体服务器是否只断开攻击连接或影响整个进程尚未验证。不得把它升级为已证明的远程代码执行、任意文件读取或P0。

权限在common命令树和权杖service中检查；选择包依赖服务器锁定会话，重检权限/持有物/目标。客户端reported definitions只是ID，不是任意文件路径或服务器权威JSON。本次没有确认越权修改他人光环的漏洞。OBJ importer不解析MTL/URL/可执行指令，mesh resource字段有path校验，但legacy定义与所有loader的预算保护不等价。

发布器默认dry-run、禁止有授权头的redirect、检查release/tag/provenance和最终正文hash，用intent/receipt防不确定重试重复上传。这些保护已存在且发布脚本mock测试通过。HTTP错误detail仍包含经过截断的远端正文，若以后扩展错误日志，需注意可能的敏感内容反射；没有证据证明当前真实token泄露，不列为确认漏洞。

HALO-014是内容级依赖校验/高权限actions固定的P3建议。没有完成针对全部平台传递依赖的漏洞数据库/许可证合规审查，没有读取secret接口或查找真实凭据；不能宣称整个依赖树无CVE。HALO-015的自制聊天ack状态是兼容风险，目前没有服务端拒绝/断线的实际结果。

## 性能、耦合与技术债务

HALO-010将持久状态线性列表与所有living entity加载事件结合，产生O(E×N)查找；实际store操作计数分别达到约5000万和2000万。未做游戏TPS或JFR，因此报告只给操作量，不伪造时延。HALO-011的缓存生命周期、HALO-008的预算和HALO-003的CPU fallback也会在适当负载下放大资源成本。

core与平台的bytecode边界实际检查通过。服务器/客户端实例分离、共享中立FrameOutput、legacy与cached提交复用、native存储归平台等结构合理。适配器仍有注册/日志类型引用环和全局facade；没有类初始化死锁或运行时循环的证据，不把源码互相import本身当缺陷。命令树与字符串handler有重复参数/反馈逻辑，可在未来改进中统一契约，但没有因此新增一个仅基于代码风格的finding。

物理与动画大量边界已有测试；本次没有给每个旋转公式做独立数学证明。仓库历史性能文档报告了具体硬件/版本和人工验收，它是历史证据而不是本次测量。缓存quad的本次复现与历史验收材料之间存在差异，应按精确SHA/实际factory日志重跑对应用例，而不是笼统否认全部历史数据。

## 测试、CI与构建可靠性

- 发布Python测试48项通过，均mock外部调用。

- GitHub基线提交的Java CI与发布器测试均success；远端build job的core检查、联合build与artifact步骤success；普通branch run的Release步骤skipped。
- 无专门Lint/SpotBugs/Checkstyle/覆盖率任务；Java类型检查只由编译覆盖，不能说有单独静态分析gate。

HALO-013指出现有测试镜像上传错误公式，以及C2S恶意输入缺少行为测试。YSM发布包签名测试缺变量时跳过，CI配置没有注入该变量；本次没有读取远端逐测试结果，不能给它编造实际跳过数。GUI/GL/第三方真实ABI验收也没有本次环境。

## 优先解决的10项

选择依据依次是：远端输入安全与恢复阻断；有效数据被破坏；默认资源加载的边界；可重复的共享状态错误；已有功能中必然触发的fallback及随规模增长的成本。先保证错误可观测/可拒绝，再优化；确认程度和修复可验证性同样参与排序。

| 顺序 | 编号 | 级别 | 优先理由 |
| --- | --- | --- | --- |
| 1 | HALO-001 | P1 | 无管理员门槛的远端输入可触发OOM级分配 |
| 2 | HALO-002 | P1 | 写入后校验失败，并在持久记录恢复时重复发生 |
| 3 | HALO-004 | P2 | 已复现单条坏值删除后续有效服务器数据 |
| 4 | HALO-005 | P2 | 本地佩戴与配置缺少写入失败/中断时的旧数据保护 |
| 5 | HALO-007 | P2 | 小型合法JSON可绕过普通坏资源隔离 |
| 6 | HALO-008 | P2 | 小型定义可请求百MiB级几何，缺少事前预算 |
| 7 | HALO-003 | P2 | cached billboard稳定越界并fallback，直接影响已发布功能 |
| 8 | HALO-009 | P2 | 动画结果可修改共享定义状态，存在明确所有权缺口 |
| 9 | HALO-010 | P2 | 所有实体加载与持久佩戴规模产生乘积扫描 |
| 10 | HALO-011 | P2 | 长会话同代际定义轮换持续保留已移除CPU模型 |

HALO-006可与005一起以较小工作量解决；HALO-013是前述修复的验收前置，不应等主功能修完才补门禁。HALO-012/015先验证再决定修复；HALO-014安排后续构建加固。
