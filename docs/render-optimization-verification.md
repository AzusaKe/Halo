# 2.3.1 渲染优化与验收记录

本轮只跟进 Minecraft 1.20.1 Fabric 主线及其锁定的 core，功能版本 `2.3.1`、适配版本 `2.3.1+adapter.1`。基线是 Halo `f4523c443087e4eb05c51476d6e5771653ca8d3c` / core `4b4f7bb1f7dea99d86fd46d451f5bc4b016404eb`。不修改 flash 分支、API v2、定义 JSON、存档或网络协议。

## 使用方式

`config/halo-azusake/halo_mod_config.json` 中的 `primitiveRenderBackend` 支持：

| 值 | 行为 |
| --- | --- |
| `compatibility`（默认） | 共用预生成的局部几何，展开为原有即时顶点；只合并相邻且绘制状态相同的批次 |
| `cached` | 使用静态 GPU 几何和逐图元变换；沿用旧图元材质、原顺序和提交阶段 |

`/halo renderer` 查询；`/halo renderer compatibility` 或 `/halo renderer cached` 切换并保存。缺失、null、非字符串或未知值均恢复为 `compatibility`，其他配置和未知字段保留。命令不要求服务器权限，也不转发到服务器。下一帧开始时一次采样设置，同时应用于世界和 GUI；不会重置佩戴、物理或动画。已有 OBJ mesh 不受该设置影响。

兼容模式适合大量同材质、相邻 billboard；缓存模式在较多 ring 顶点或材质交替时可能更合适。缓存模式不是统一更快的开关。若某个光影组合出现显示问题，可立即切回兼容模式；此开关不替代回归修复或验收。

## 实现边界

- core 按形状参数共享不可变局部几何。ring 内外面保留独立法线、原绕序、分段数和接缝 UV；billboard 兼容输出仍是四边形，缓存三角形对角线为 `0,1,2 / 2,3,0`。`face_camera` 继续使用世界/正交预览的原有朝向计算。
- 兼容展开只计算一次共享顶点，保留完整源顶点序列。纹理可用性只在单次渲染调用内去重。相邻合并核对纹理、拓扑、材质、光照、方向光、统一颜色/透明度和深度/剔除状态；顶点自己的颜色仍逐顶点保留。
- 缓存提交复用 `HaloMeshBufferCache`、原生/Iris 材质及状态恢复设施。保持旧透明度截断、顶点颜色的字节量化和光照顺序。旧图元不进入 OBJ 透明排序队列，不逐帧排序或上传静态索引，也不对镜像变换额外翻转绕序。
- 受光 billboard 上传时保留四角输入，使 Iris 继续生成原来的切线/UV 中点，再使用同一对角线索引。共用上传暂存 builder 在成功/异常路径显式释放 `GlAllocationUtils` 的原生 malloc；GPU 同步上传完成后才释放，不依赖无 cleaner 的 ByteBuffer 被 GC。
- 在客户端资源加载/定义刷新时准备几何、纹理，缓存模式的 GPU 上传发生在渲染线程。切回兼容模式释放图元 GPU 缓冲；资源代次、定义移除、光影格式变化及客户端退出负责更新/释放。专用服不准备绘图几何。
- 上传异常被记录并记忆，重载或重新启用缓存模式时重试；缺失或代次不符的缓冲在提交前从同一帧命令展开回退。回退不再调用模拟、不重复绘制。未纹理化或缺少相应原生光照格式的命令继续使用兼容提交。
- 旧 `FrameScene`、`PreviewFrame`、`FrameOutput` 构造器和访问器保留。新模式只输出一种旧图元表示；`expandedBatches()` 同时支持新命令。`DefinitionSnapshot` 原有 mesh 依赖含义不变，另提供只读旧图元依赖和几何入口。

## 自动验证

Java 17 独立 core 构建、Halo 联合构建与打包检查；314 项 core 测试及 111 项 Halo 测试均通过，无失败/错误/跳过。Halo 测试提供了实际 YSM 2.6.5 发布 JAR，签名检查未跳过。另通过平台边界扫描、最终 JAR 合包/来源检查、旧锚点 API v2、外部预览提供者、旧 ClientPort 以及本轮新增的冻结 2.3.0 帧/预览/输出构造器二进制调用方检查。

冻结旧 `SceneRenderer` 和旧 collector 为独立数值参照。固定时间/实体/相机，对照原实现、兼容模式和缓存展开，检查位置、UV、颜色、状态、顺序、有效法线及物理输出；位置/法线浮点容差为 `2e-6`。覆盖发光/受光、缺失纹理、双纹理与双面 ring、UV 接缝、面对相机、非均匀/镜像/零缩放、大坐标和透明度。另检查配置修复/保存、共享资源、矩阵防御性复制、表示互斥、预览切换不重置状态、合批边界、上传失败记忆与资源释放。

## 2026-09-16 反馈复核：命令补全与性能数据撤回

用户指出 `/halo renderer` 没有候选，并观察到性能测试玩家掉下平台。复核确认两点：

- 当前 Fabric 客户端命令复制先合并空根节点、再给临时节点添加子节点。服务端已有 `/halo` 时，新客户端子节点未附着到最终树。游戏内复现为：无 OP 时有 renderer 候选，授予 OP 后候选消失；直接输入仍执行成功。现复用同一 renderer 字面量定义，为已存在的根节点补全子树；根节点不存在时让 Fabric 完整复制，保留 list 等其他客户端候选。命令树重载、权限变化、重连均重新处理，执行仍只走客户端。
- 原性能脚本将玩家传送至 `(0,82,14)`，平台却只铺到 `z=12`；玩家会跌至草地，旧探针没有检查采样期间的位置和可见性。视野外 Halo 仍可能计算并提交，因此提交计数非零不能证明光环正在屏幕内。先前的整帧/CPU/分配/GC 对照及 `13.20 → 4.12 ms` 等结论全部撤回，不能用于证明正常观看时的收益。原文件保留供审计，原验证目录增加 `PERFORMANCE-WITHDRAWN.md`。

构建、数值/ABI 回归、生命周期及独立截图验证与此无效性能场景分开记录。玩家体感卡顿减少是有价值的反馈，但不能单凭它断言优化已消除卡顿。

## 修正后的性能方法

继续使用上述机器和固定画质。六个场景为：20 × 32 billboard、20 × 8 同纹理 ring、20 × 8 交替纹理 ring、1 × 128 ring、1 × 32 billboard、1 × 8 ring；ring 为 32 分段，性能夹具均使用发光材质。对照原始基线、兼容模式和缓存模式，每场景三轮。正式分辨率矩阵全部使用同一整合包副本，无光影组仅关闭 Iris 光影，不移除其他模组；受光和 OBJ 混合属于前述功能回归，不把这些合成负载的 FPS 推广到所有材质。

平台扩展至 `x/z=-20..20`，玩家脚部固定在 `(0,80,14)`，眼睛高度另行验证。猪关闭 AI/重力。服务端完成场景准备、客户端同步稳定后再预热；每轮采样前后保存实际画面。逐帧验证平台支撑、玩家/相机坐标、猪数量、佩戴数量和视锥内数量，偏离即整次测试失败，不把错误视角下的帧计为成功。

每轮 5 秒：前 2 秒看阵列，第 2–3 秒转向空区，之后转回。相机 yaw/pitch 在渲染帧开始前设置，避免帧末改角造成一个采样帧的错位；记录实际可见性以区分两段。统计表只使用阵列入镜帧，空区样本单独保留；转回后 200 ms 峰值从实际 `away → visible` 边界计算。每轮之间有预热间隔，截图/写 CSV 均在采样窗外，JFR 区间使用探针记录的起止时间而非文件修改时间估计。

CSV 逐帧保存位置、yaw/pitch、眼睛高度、期望/在场/视锥内猪数量及 away 标记，同时保存帧耗时、Halo CPU、分配、提交和上传量。所有构建使用相同探针/JFR 设置；探针存在固定观测开销，结果属于本机合成场景。CPU/分配来自 `HaloRenderer.renderHalos`，不包含 OBJ 后续独立提交。各轮统计 P50/P95/P99/峰值，汇总取三轮统计值中位数，峰值取最大。

## RenderScale 复核与统一分辨率矩阵

用户进一步指出整合包启用了 RenderScale。隔离副本的实际配置为 `scale=1.0`、`irisScale=0.5`；旧报告把窗口尺寸当作光影内部尺寸，不能用于跨光影或原生分辨率的比较。此前 1280×720 窗口下的整合包数据撤出正式性能结论，保留在修正目录供追溯。

按用户补充要求，新建独立副本，移除 RenderScale JAR，保持其余整合包一致。分别测 1920×1080 和 3840×2160，全屏、相同显示刷新率、VSync 关闭、不限帧。在无光影、BSL_v10.1.1、iterationRP Alpha 0.8.28 下，对照基线、compatibility、cached，共 18 个组合；每组合继续使用六个场景、每场景三轮。BSL 先于 iterationRP 执行。

探针在游戏中确认 RenderScale 未加载；逐帧核对窗口 framebuffer、Minecraft 主 framebuffer、Iris 基础渲染目标的尺寸。每轮采样前后另用 OpenGL 读取主颜色纹理实际宽高；录制中资源代次或光影 pipeline 改变会直接报错。显示模式、缓冲尺寸、配置与模组/构建 SHA 随原始数据保存。光影自身为阴影、泛光等辅助效果采用的不同分辨率不改写。

BSL 首轮截图发现全屏切换后绿色远景遮住近处平台和猪，旧基线与新兼容模式均复现，坐标/视锥断言无法发现这种合成异常。单独关闭景深未能在相同全屏条件下解决；按用户建议，在保持 BSL 原选项（包括景深、运动模糊）不变时重载光影，近处场景恢复。正式光影测试在分辨率切换完成后调用 Iris 重载，再预热和采样；采样期间禁止 pipeline/资源代次变化。此准备步骤只属于测试探针，不改变 Halo 的日常光影切换行为。异常样本隔离保存，不纳入统计。该现象与当前 Iris/Distant Horizons 光影组合有关，但本轮未定位内部根因，不能把重载恢复等同于已证明某个具体模组的绘制顺序错误。

### 结果解读与限制

默认兼容模式的收益在高图元数量下可重复观察到。例如 20 × 32 billboard：无光影 1080p 为 135.3 → 250.9 FPS，BSL 1080p 为 68.9 → 138.2 FPS，iterationRP 1080p 为 65.1 → 93.4 FPS；相应提交从 640 次合并为 1 次。BSL 1080p 此场景三轮基线范围 68.38–69.29 FPS，兼容范围 138.00–138.49 FPS，没有重叠。

日常较轻场景的绝对收益小得多：1 × 32 billboard 在 BSL 4K 为 42.1 → 42.8 FPS，在 iterationRP 4K 为 25.1 → 25.2 FPS。这与“平均帧率提升体感不明显”相符。结合分辨率变化和 Halo 提交耗时，推测此类场景主要受光影/GPU 工作限制；本轮未单独测 GPU 执行时间，不能把推测当作 GPU 分析结论。

缓存模式有明确适用场景：无光影 1080p、20 × 8 交替纹理 ring 为 123.1 → 233.8 FPS，1 × 128 ring 为 194.7 → 481.1 FPS。全部 108 轮缓存模式的稳态上传量最大值均为 0。但它保留每个原图元/表面的提交，不能获得兼容模式的相邻大批次收益；在多数本次光影场景中，兼容模式更快。缓存模式也未普遍改善尾部，例如 BSL 4K 大量 billboard 的三轮 P99 中位数为 42.17 ms，基线为 36.89 ms；各轮波动较大（基线 P99 为 61.75/36.20/36.89 ms，缓存为 43.84/42.17/34.86 ms），不能据此承诺尾部更稳定。

默认兼容模式在不少密集场景同时降低 P99 和转回峰值，例如 BSL 1080p 大量 billboard 的转回峰值为 17.78 → 9.39 ms；但没有在每个场景都降低。数据支持“部分场景更平稳”，不支持“所有瞬时卡顿已解决”。本次没有给出首次加载/首次入镜的等价定量帧耗时对照；其启动期读取保留在 JFR，不能与预热后的转回统计混合使用。

每轮仅 5 秒、每场景三轮，属于本机固定机位合成对照；不同组合顺序运行，未锁定处理器/GPU 频率与温度，不把小幅百分比差异解释为显著收益或回归。探针和 JFR 带来观测开销，采样期间没有并行运行构建、压缩或 JFR 解析。原始三轮值、各轮范围及完整帧耗时保留供复核。
