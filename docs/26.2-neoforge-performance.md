## Method and evidence

Each count warms for 60 seconds and has three 120-second JFR recordings, with 5 seconds between recordings. The repeats establish A/A variability. Compare the default resident path to an otherwise identical restart with `-Dhalo.mesh.forceExpanded=true`. Both use `-Dhalo.mesh.profile=true`, which enables the same diagnostics overhead.

`halo.FrameTime` measures main-camera collection intervals, not GPU presentation latency. Report frame count, median, p95, p99 and counts above 50/100 ms. Profile logs report Halo CPU submission and vertex/index upload counts/bytes every 300 frames. JFR allocation sampling is weighted and approximate; separate `Thread.print -e` snapshots measure render-thread cumulative allocation deltas. The first event in a recording may represent sampling accumulated before recording started, so weighted totals alone are not exact allocation rates.

Local evidence is under `F:/codex-cache/halo-26.2-neoforge/evidence/performance`. Host scripts and isolated data pack are outside the repository; candidate hashes are in `candidates/02/manifest.json`. Record settings and shader configuration with the results.

The initial mixed-scene sample only validated the recorder. The first controlled attempt (`cached`) is invalid: Minecraft's default AFK setting throttles an unmoving camera to 30 FPS after 60 seconds, then 10 FPS after ten minutes. This was detected and corrected before the matrix; valid recordings use `cached-r2` and the corresponding forced-expanded run.

The frozen 26.2 NeoForge flash branch supports billboard/ring but has no mesh implementation. Flash comparisons are restricted to shared primitives; it cannot supply a same-model high-poly baseline. No flash timing result is available yet.

Repeated resource reload/shader rebuild and final native/backend checks remain separate acceptance gates. No GPU execution-time or VRAM-retention claim is implied by CPU/JFR data.
