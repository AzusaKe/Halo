## Implementation

RenderPearl requires resources to be uploaded before entering a render pass. Halo prepares immutable draw submissions before the world/PIP passes; the solid pass consumes the early list and the post-framegraph stage consumes the late list. Transient resources survive until the frame ends. Transparent mesh instances and previews get separate reusable index slots so later preparation cannot overwrite queued indices. Geometry, native/Iris vertex streams, exact sorting revisions and same-frame CPU fallback are retained.

Native GLSL uses 26.3 includes and explicit interface locations. Iris owns compiled pipeline wrappers; Halo selects its private program inside the pipeline lookup and extends only its material UBO/mask bindings. Resource/shader reloads invalidate resident streams. First-person camera quaternions, shadow isolation, EMF base-model identity and preview first-frame pointer seeding are retained. Preview heads are captured during model preparation and Halo draws into the actual PIP render pass.

No core production/API/schema/storage/protocol changes. No YSM or Vulkan shader support is added.

## Issues resolved during migration

- Initial startup: GameRenderer.render no longer accepts DeltaTracker/boolean; frame lifecycle hook updated.
- First world draw: resource upload inside an open RenderPass was rejected. Preparation and submission are now separate.
- Native shader compilation: obsolete moj_import directive replaced by includes and explicit locations.

These failed runs are retained as diagnostics (`native`, `native-r2`, `native-r3`) and are not counted as passed acceptance.

- Iris mask regression: RenderPearl reflects/reorders binding layouts. Resolve HaloMaterial/HaloMask indices from each compiled pipeline, preserving Iris native/PBR bindings. User confirmed the fix; two layout regression tests pass (`halo-263-mask-regression.log`).
- Deferred transient indices: resolve the current shared sequential buffer at submission, because later preparation can grow and close its earlier allocation.
- Optional JFR `halo.Frame` event (disabled by default) records host frame intervals and resident geometry/sorted-index upload counts. Profile with `jfr configure --input profile.jfc --output halo.jfc +halo.Frame#enabled=true`, then attach with `jcmd <pid> JFR.start settings=halo.jfc duration=90s filename=halo.jfr`. Frame intervals include the host frame limiter and all rendering, not just Halo.

## Performance scope

The two recordings used the user-selected high-polygon scene, IterationRP 0.8.28, and the same requested fixed view. Each scheduled recording was 90 seconds and is divided into three 30-second windows. Host frame intervals include all game rendering and frame limiting. One cached window has a p95 spike; the final compatibility window has fewer recorded frames. Foreground state and interruptions were not independently controlled, so these data do not establish a cross-version speedup or a strict no-regression benchmark. Sampled allocations are estimates. Iris tangent samples also include Minecraft geometry and cannot be attributed to Halo solely by method name. Both Halo modes recorded zero resident geometry reuploads; transparent sorted indices continued updating. The maintainer accepted the current performance and subsequently approved release.
