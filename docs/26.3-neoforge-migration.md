# Minecraft 26.3 NeoForge migration

Status: platform migration and the recorded automatic/native/Iris/EMF checks are complete. The maintainer accepted the optimization as meeting expectations and requested stopping the remaining pressure tests on 2026-10-12 after reporting the laptop was in quiet mode. Recorded timings are diagnostic, not a completed quantitative acceptance matrix. Network testing is maintainer-owned; tags and GitHub Release await an explicit later publication request.

- Intended target version: `2.5.0+adapter.1`.
- Evidence, dependency manifest and isolated instances: `F:/codex-cache/halo-26.3-neoforge`.

World extraction collects one core `renderFrame` output. NeoForge `PrepareRenderBuffersEvent` prepares early/late GPU commands before active render passes. `AfterOpaqueFeatures` consumes the early commands using its supplied pass. The frame-graph completion hook consumes late commands before Iris composites. Preview model preparation captures a separate head pose, prepares commands before its PIP pass and submits inside that pass. Preview startup must not reset world capture.

First person retains camera quaternion conversion. Repeated stages and shadow passes cannot advance simulation or consume main-frame output. Native/Iris resident layouts, Iris triangle-corner and four-corner attributes, generation-based resource disposal and same-frame CPU fallback remain. Deferred transparent instances and previews own separate reusable sorted-index slots. Transient allocations remain alive until frame completion; shared sequential index allocation is resolved at draw time after preparation requests its capacity.

No new core public API, schema, saved-data or wire format is introduced. Preserve `halo:world_data`, `Halos`/`UUID`/`Definition`, lenient string/integer-array UUID reads, canonical integer-array writes, configuration unknown fields and current-empty-file suppression of legacy imports. Bidirectional compatibility means Halo data round trips, not downgrading an entire Minecraft world. No YSM, Caustica or Vulkan shader integration is added.

### Loader/Sodium compatibility boundary

The first ordinary .76 Iris startup fails in Sodium's `platform.neoforge.LevelExtractorMixin`: the required four-argument `extractVisibleBlockEntities(Camera,float,LevelRenderState,Frustum)` no longer exists. Inspection of official NeoForge patches locates the removal at .65; .64 retains the method. Both Sodium 0.9.2 and 0.9.3-alpha.1 contain the old descriptor. This is an upstream compatibility limitation, not a passed Halo shader test. The maintainer explicitly selected .64-beta as the minimum/default shader baseline while retaining .76 native verification. No third-party jar is patched or redistributed.

Performance compares 26.2/26.3 and resident/forced-expanded target paths using the same approximately 96k-face model at 1/8/16 instances. Use 1920x1080 fullscreen, fixed world/camera/settings, controlled VSync/frame cap and disabled AFK throttling. Warm up 60 seconds, sample 120 seconds, repeat three times. Record median/p95/p99 frame times, Halo CPU preparation/submission, sampled allocations and vertex/index upload counts/bytes. Repeatable median/p95 regression above 10% and beyond A/A variability requires investigation and correction or explicit maintainer acceptance. No gain or GPU execution-time claim without appropriate measurements.

The initial cached-path attempt is invalid and archived separately: the setup function first had an invalid multi-entity hide selector, then creative mode allowed the observer to fall away from the models; the fullscreen mode also reverted to 3840x2160. None of those recordings enter comparisons. The corrected fixture uses spectator mode at `(1024.5,202,1015.5)`, yaw 0/pitch 10, waits for forced chunks before building the stage and centers the first wearer at `(1024.5,200,1023.5)` in front of the camera. The `.5` Z centers follow Minecraft's integer X/Z command-coordinate semantics. Setup only prepares a visible one-halo scene; explicit `halo_benchmark:begin` starts sampling after maintainer visual confirmation. Video-mode persistence uses the version-specific format (26.2 string, 26.3 JSON), and the target recorder verifies the 1920x1080 exclusive-mode log before recording.
